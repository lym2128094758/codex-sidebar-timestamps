# 架构与维护说明

## 长期维护基线

`0.2.2`（提交 `8343777`）是本项目的长期维护基线。Windows Codex 的原有聊天行负责布局和滚动，插件在行内添加最后活动时间。鼠标进入和离开时，时间随行末按钮的变化向左移和向右回，动画约 180 毫秒，并尊重系统的减少动态效果设置。

## 运行方式

| 部分 | 职责 |
| --- | --- |
| `plugins/sidebar-time/.codex-plugin/plugin.json` 与 `plugin.json` | 声明插件身份、版本和显示信息。 |
| `skills/toggle/` | 提供开启、关闭和查询状态的命令。 |
| `runtime/client-patch.py` | 读取插件配置和本地 SQLite 数据，通过仅限本机的 Chromium 调试接口，将时间映射交给 Codex 页面。后台进程按约 3 秒的间隔刷新数据。 |
| `runtime/client-patch.js` | 按聊天行上的会话 ID 插入 `<time>`，由原有布局处理长标题和操作按钮。通过 `MutationObserver` 与 `requestAnimationFrame` 合并页面更新，并用 `ResizeObserver` 和 Web Animations API 实现行内滑动。 |

Python 以只读方式打开 `state_5.sqlite`，优先取最近活动时间，缺失时取更新时间。JS 通过 `data-app-action-sidebar-thread-id` 查找记录，找不到时显示「时间未知」。重复标题各自保留自己的时间。停止补丁会清除时间标签并解除观察器。

安装或启用插件后，仍需要一个提供本机调试接口的 Codex 实例。开发和维护时只使用回环地址。普通启动的现有进程如果没有调试接口，补丁无法连接。启动器可以放在插件外单独维护，启动流程的改动不应改变行内布局、动画或数据匹配。

## 为什么覆盖层方案退步

后续在本机试过 `0.2.3` 的 Windows UI Automation 加 WPF 透明覆盖层，目的是适配从普通入口启动的 Codex。它能在窗口外画时间，但无法参与聊天行的原有布局。

| 用户看到的问题 | 实现原因 |
| --- | --- |
| 动画慢、快速划过时不动 | 悬停状态在扫描时才读取。最后一版的扫描间隔为 2 秒，即使位移动画同样是 180 毫秒，仍可能延迟触发或漏掉。 |
| 滚动时卡顿，时间跟不上聊天行 | 覆盖层周期性扫描客户端的无障碍树，行位置变化后还要重建标签。把间隔从 550 毫秒延长到 2 秒减少了扫描次数，同时加重了跟随延迟。 |
| 有些时间缺失或可能串行 | 无障碍树的行类型、尺寸和可见状态都影响识别。覆盖层只能用标题和项目名匹配，取同名记录里最新的一条可能显示成另一场聊天的时间。 |
| 长标题和时间容易挤在一起 | 覆盖层只能按屏幕坐标放文字，无法给时间预留布局空间，也无法让原生标题按剩余宽度截断。 |

覆盖层是一次启动兼容性实验。后续维护以行内布局、会话 ID 匹配和由页面布局变化触发动画为准。

## 后续维护

- Codex 升级后，先检查当前实例是否提供本机接口，再分开检查聊天行选择器和数据库字段。没有会话 ID 对应关系时显示「时间未知」，不按标题猜测。
- 保持动画随操作按钮即时触发。改启动方式时，不把鼠标悬停和滚动跟随交给后台扫描。
- 更新前在目标 Windows 客户端检查短标题、长标题、同名聊天、置顶和归档按钮、滚动、移入移出动画、减少动态效果设置，以及关闭后清除时间。记录实际验证过的客户端版本和启动方式。
